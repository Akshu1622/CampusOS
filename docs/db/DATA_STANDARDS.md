# Global Data Standards and Database Conventions

This normative document defines the data standards, conventions, and operational rules for the University ERP database. All later phases must strictly obey these rules.

## 1. Naming Conventions
- **Tables**: Plural (e.g., `users`, `students`, `courses`).
- **Columns**: `snake_case`, descriptive (e.g., `first_name`, `is_active`).
- **Primary Keys**: Surrogate key named `id` for every table.
- **Foreign Keys**: `<referenced_table_singular>_id` (e.g., `student_id`).
- **Indexes**: `idx_<table_name>_<column_name>` (e.g., `idx_students_last_name`).
- **Unique Constraints**: `uq_<table_name>_<column_name>` (e.g., `uq_users_email`).
- **Check Constraints**: `chk_<table_name>_<condition>` (e.g., `chk_courses_credits_positive`).
- **Views**: Prefix with `vw_` (e.g., `vw_active_students`).
- **Functions**: Prefix with `fn_` (e.g., `fn_calculate_gpa`).
- **Procedures**: Prefix with `sp_` (e.g., `sp_enroll_student`).
- **Triggers**: Prefix with `trg_`, suffix with `_b`/`_a` and `_i`/`_u`/`_d` (e.g., `trg_students_b_i` for Before Insert).

## 2. Global Identifiers
Every foreign key to a global identifier must use exactly the same type, length, charset (`utf8mb4`), and collation (`utf8mb4_0900_ai_ci`). Global identifiers act as unique business keys alongside a surrogate `id` (BIGINT AUTO_INCREMENT primary key). Using surrogate keys for PK ensures efficient joins and immutability, while business keys provide readable, robust identification.

### A. Student ID
- **Format**: `STU-YYYY-NNNNNN` (e.g., `STU-2023-000123`).
- **Length**: 15 characters (`VARCHAR(15)`).
- **Regex**: `^STU-[0-9]{4}-[0-9]{6}$`
- **Generated By**: Database function `fn_generate_student_id` using a sequence generator.
- **When**: Before INSERT trigger on `students`.
- **Uniqueness Scope**: Global across the entire ERP.
- **CHECK Expression**: `student_id REGEXP '^STU-[0-9]{4}-[0-9]{6}$'`
- **Examples**: `STU-2023-000123`, `STU-2024-000001`, `STU-2022-999999`.

### B. Employee ID
- **Format**: `EMP-YYYY-NNNN` (e.g., `EMP-2023-0012`).
- **Length**: 13 characters (`VARCHAR(13)`).
- **Regex**: `^EMP-[0-9]{4}-[0-9]{4}$`
- **Generated By**: Database function `fn_generate_employee_id`.
- **When**: Before INSERT trigger on `employees`.
- **Uniqueness Scope**: Global.
- **CHECK Expression**: `employee_id REGEXP '^EMP-[0-9]{4}-[0-9]{4}$'`
- **Examples**: `EMP-2023-0012`, `EMP-2024-0001`, `EMP-2022-9999`.

### C. Course Code
- **Format**: `[A-Z]{2,4}[0-9]{3,4}` (e.g., `CS101`, `MATH2001`).
- **Length**: VARCHAR(10).
- **Regex**: `^[A-Z]{2,4}[0-9]{3,4}$`
- **Generated By**: Admin/User input.
- **When**: On course creation.
- **Uniqueness Scope**: Global.
- **CHECK Expression**: `course_code REGEXP '^[A-Z]{2,4}[0-9]{3,4}$'`
- **Examples**: `CS101`, `MATH2001`, `ENG101`.

### D. Receipt Number
- **Format**: `RCP-YYYYMMDD-NNNNN` (e.g., `RCP-20231025-00001`).
- **Length**: 20 characters (`VARCHAR(20)`).
- **Regex**: `^RCP-[0-9]{8}-[0-9]{5}$`
- **Generated By**: Database function `fn_generate_receipt_number`.
- **When**: Before INSERT trigger on `payments`/`receipts`.
- **Uniqueness Scope**: Global.
- **CHECK Expression**: `receipt_number REGEXP '^RCP-[0-9]{8}-[0-9]{5}$'`
- **Examples**: `RCP-20231025-00001`, `RCP-20240101-99999`, `RCP-20231101-00123`.

### E. Academic Term Identifier
- **Format**: `YYYY-(FALL|SPRING|SUMMER|WINTER)` (e.g., `2023-FALL`).
- **Length**: 15 characters (`VARCHAR(15)`).
- **Regex**: `^[0-9]{4}-(FALL|SPRING|SUMMER|WINTER)$`
- **Generated By**: Admin/User input.
- **When**: On term creation.
- **Uniqueness Scope**: Global.
- **CHECK Expression**: `term_id REGEXP '^[0-9]{4}-(FALL|SPRING|SUMMER|WINTER)$'`
- **Examples**: `2023-FALL`, `2024-SPRING`, `2022-SUMMER`.

### F. Payment Reference
- **Format**: `PAY-[A-Z0-9]{12}` (e.g., `PAY-A1B2C3D4E5F6`).
- **Length**: 16 characters (`VARCHAR(16)`).
- **Regex**: `^PAY-[A-Z0-9]{12}$`
- **Generated By**: Payment gateway or internal random generator `fn_generate_payment_ref`.
- **When**: On payment initiation.
- **Uniqueness Scope**: Global.
- **CHECK Expression**: `payment_reference REGEXP '^PAY-[A-Z0-9]{12}$'`
- **Examples**: `PAY-A1B2C3D4E5F6`, `PAY-1234567890AB`, `PAY-XYZ123ABC987`.

### G. Bulk-Enrollment Batch ID
- **Format**: `BAT-YYYYMMDD-NNNN` (e.g., `BAT-20231025-0001`).
- **Length**: 17 characters (`VARCHAR(17)`).
- **Regex**: `^BAT-[0-9]{8}-[0-9]{4}$`
- **Generated By**: Database sequence function `fn_generate_batch_id`.
- **When**: Before INSERT trigger on batch job table.
- **Uniqueness Scope**: Global.
- **CHECK Expression**: `batch_id REGEXP '^BAT-[0-9]{8}-[0-9]{4}$'`
- **Examples**: `BAT-20231025-0001`, `BAT-20240101-9999`, `BAT-20231101-0123`.

### H. Payroll Month Key
- **Format**: `YYYY-MM` (e.g., `2023-10`).
- **Length**: 7 characters (`VARCHAR(7)`).
- **Regex**: `^[0-9]{4}-(0[1-9]|1[0-2])$`
- **Generated By**: System derived from payroll dates.
- **When**: On payroll generation.
- **Uniqueness Scope**: Global per employee.
- **CHECK Expression**: `payroll_month REGEXP '^[0-9]{4}-(0[1-9]|1[0-2])$'`
- **Examples**: `2023-10`, `2024-01`, `2023-12`.

## 3. Data Types
- **Surrogate Keys**: `BIGINT AUTO_INCREMENT PRIMARY KEY`.
- **Shared-Key VARCHAR Lengths**: Consistent lengths (e.g., 255 for standard descriptive keys, specific lengths for global identifiers).
- **Money**: `DECIMAL(15, 2)` (precision 15, scale 2).
- **Percentages**: `DECIMAL(5, 2)` (e.g., 100.00).
- **Dates and Timestamps**: `DATETIME` or `TIMESTAMP` in UTC. Default: `CURRENT_TIMESTAMP`.
- **Booleans**: `TINYINT(1)` (1 for true, 0 for false).
- **ENUM vs Lookup Table**: Use ENUM only for states that change very rarely (e.g., `GENDER ('M', 'F', 'O')`). Use lookup tables for business categories (e.g., Departments, Job Roles).
- **Text Lengths**: `VARCHAR(255)` for short text (names, emails), `TEXT` for longer unstructured data.
- **JSON**: Use `JSON` data type strictly for unstructured/semi-structured metadata. Must not contain relational data or references.

## 4. Common Columns
- Every table MUST have:
  - `created_at DATETIME DEFAULT CURRENT_TIMESTAMP`
  - `updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`
  - `created_by BIGINT NULL` (References user ID)
  - `updated_by BIGINT NULL`
- **Exemptions**: Mapping tables (many-to-many join tables) and log/history tables.
- **Status Columns**: No hard deletions. Use `status ENUM('active', 'inactive', 'deleted') DEFAULT 'active'` or `is_active TINYINT(1) DEFAULT 1`.
- **Referential Actions**: `ON DELETE RESTRICT` and `ON UPDATE RESTRICT` by default. Exceptions: `ON DELETE CASCADE` is allowed only for child records that make no sense without their parent (e.g., `invoice_items` cascading from `invoices`).
- **History Retention**: Audit triggers insert into `_history` tables for critical data (e.g., financial transactions, grades).

## 5. Constraint Patterns
For rules without native MySQL syntax (e.g., "only one active row per key"), use a generated column that evaluates to the key when active and `NULL` otherwise, plus a `UNIQUE` index.
**Technique snippet**:
```sql
ALTER TABLE hostel_allocations
  ADD COLUMN active_student_id BIGINT GENERATED ALWAYS AS (IF(status = 'active', student_id, NULL)) VIRTUAL,
  ADD UNIQUE INDEX uq_hostel_allocations_active (active_student_id);
```

## 6. Error-Handling Convention
Stored programs must use `SIGNAL SQLSTATE '45000' SET MYSQL_ERRNO = <code_number>, MESSAGE_TEXT = '<message>'`.
Numeric range per module (>50000):
- **M1 Core**: 51000 - 51999
- **M2 Academics**: 52000 - 52999
- **M3 Exams**: 53000 - 53999
- **M4 Finance**: 54000 - 54999
- **M5 HR**: 55000 - 55999
- **M6 Hostel**: 56000 - 56999
- **M7 Analytics**: 57000 - 57999

The FastAPI backend captures `MYSQL_ERRNO` > 50000 and maps it to HTTP 400 (Bad Request) or 409 (Conflict) depending on the context, extracting `MESSAGE_TEXT` as the API response message.

## 7. Stored-Program Conventions
- **Parameters**: Prefix with `p_` (e.g., `p_student_id`).
- **Variables**: Prefix with `v_` (e.g., `v_total_amount`).
- **Transactions & Isolation**: Use `REPEATABLE READ` (MySQL default). Explicit `START TRANSACTION` and `COMMIT`/`ROLLBACK` in procedures.
- **Row-Locking**: Use `SELECT ... FOR UPDATE` before updating records to prevent concurrency issues (PRD §11.6).
- **Triggers**: Never use `COMMIT` or `ROLLBACK` inside triggers (MySQL forbids this anyway).
- **DELIMITER**: Use `//` as the delimiter for stored programs in scripts.
- **Return Values**: Use `OUT` parameters for simple status/ID returns; use result sets (`SELECT`) when returning tables of data.
- **Header Comment Template**:
```sql
-- ==========================================================
-- Purpose: [Description]
-- Inputs: [List of p_ arguments]
-- Outputs: [List of OUT arguments or Result Set description]
-- Errors: [List of SIGNAL errors thrown]
-- Author: [Name]
-- Date: [YYYY-MM-DD]
-- ==========================================================
```

## 8. Documentation Conventions
- **Comments**: Use the `COMMENT` clause on EVERY `CREATE TABLE` and `COLUMN` definition.
  - Example: `status VARCHAR(10) COMMENT 'Current status of the student'`
- **Data Dictionary**: Keep updated in markdown under `docs/db/schema_doc.md` (generated or maintained manually).

## 9. Test Conventions
- **Layout**: Test scripts reside in `db/tests/`.
- **File Naming**: `<phase_num>_<module>_test.sql` (e.g., `00_foundation_test.sql`).
- **Expected Output Capture**: Use `mysql --table` format. Output is saved to `docs/db/proofs/`.
- **Pass/Fail Convention**: Tests should visually output `PASS: <Condition>` or `FAIL: <Condition>`. Python wrappers (like `db_exec.py`) should parse failures or exit non-zero on `SIGNAL SQLSTATE`.
